# AI 产品经理面试回答手册：LLM 数据分析 Agent

## 30 秒项目介绍

我独立做了一个面向业务人员的 LLM 数据分析 Agent，目标是让不会 SQL 的用户也能通过自然语言完成标准化查数和自动出图。系统不会让大模型直接生成最终数字，而是先通过 Function Calling 生成结构化分析计划，再由语义层确认指标口径，经过只读 SQL 安全校验后调用 DuckDB 计算，最后用 Pandas 做结果质检并自动选择图表。这样既提升了交互效率，也控制了字段幻觉、口径错误和危险 SQL 风险。

## 两分钟项目介绍

这个项目的灵感来自我做信贷数据分析时的真实体验。很多业务问题并不复杂，例如查看不同信用等级的违约率、各渠道的审核时长或者月度申请趋势，但完整流程仍然需要确认口径、写 SQL、核对结果和制作图表。业务人员需要排队等分析师，分析师也会花很多时间重复取数。

我把产品拆成五层。第一层是自然语言入口；第二层是规划器，把问题转换成指标、维度、筛选、排序和图表类型；第三层是语义层，集中管理违约率和审批通过率等口径；第四层是执行与安全层，只允许访问白名单表和字段，并拦截 DDL、DML、外部文件读取和多语句；第五层负责 Pandas 质检、自动出图、事实摘要和审计日志。

我还保留了本地规划器，因此没有 API Key 时也能演示；配置 GPT 或 Claude 后，大模型会通过 `submit_analysis_plan` Function Calling 提交结构化计划。默认演示库有 10 万条合成信贷经营记录，所有数据都有明确标识。项目包含离线评测和危险 SQL 测试，但我不会把小规模评测结果包装成线上效果，也不会在没有用户实验时宣称固定提效比例。

## 为什么要用 LLM

用户表达同一个需求时可能使用不同说法，例如“通过率”“获批率”“审批率”。LLM擅长理解这种自然语言变化以及多条件组合。确定性代码则更适合执行计算、控制权限和保证复现，因此产品采用“LLM负责理解，工具负责计算”的分工。

## Function Calling 是什么

大模型不是直接返回一段随意 SQL，而是调用 `submit_analysis_plan`，提交受到 JSON Schema 约束的参数，例如：

```json
{
  "metric": "default_rate",
  "dimensions": ["grade"],
  "filters": [{"field": "application_year", "operator": "in", "value": [2025]}],
  "sort": "desc",
  "limit": 20,
  "chart_type": "bar"
}
```

程序验证参数后再生成 SQL。Function Calling 的价值不是让模型更聪明，而是让模型输出能够被程序可靠执行和校验。

## 如何控制幻觉

1. 大模型只能看到批准后的数据目录和指标定义。
2. 输出必须符合 `AnalysisPlan` 的 Pydantic Schema。
3. 指标公式由语义层维护，不由模型现场编写。
4. SQL 由确定性编译器生成，并经过 AST 安全校验。
5. 最终结论只能引用实际查询结果，同时展示 SQL、口径和样本量。
6. 空结果、小样本或缺失值会触发提示，不强行生成确定结论。

## 为什么需要语义层

“违约率”看似简单，但分母可能是全部申请、审批通过客户或者标签已成熟客户。本项目规定违约率只在“审批通过且标签有效”的样本中计算，并明确拒绝申请不进入分母。没有语义层，即使 SQL 语法正确，也可能得到业务上错误的答案。

## SQL 安全如何实现

系统只允许单条 `SELECT`，并通过 SQL AST 检查表、字段和语句类型；禁止增删改表、数据库管理命令、外部文件读取和多语句；所有查询必须有固定 `LIMIT`，数据库连接采用只读模式。生产环境还需要增加用户身份、行列级权限、查询超时和敏感字段脱敏。

## 为什么还要 Pandas

SQL负责从数据库聚合数据，Pandas负责结果层检查和轻量处理，例如检测空结果、指标空值、无穷值、小样本分组以及整理图表数据。两者分工后，数据库承担计算，Python承担产品逻辑和展示前质量控制。

## 如何评测

评测分四层：自然语言规划是否识别正确；SQL是否成功执行；危险SQL是否被拦截；结果是否包含实际数据、指标口径和SQL依据。当前评测覆盖标准场景，结果记录在 `reports/evaluation_report.json`。它不能代表开放域泛化，需要继续加入同义表达、模糊问题、对抗问题和真实用户任务。

## 为什么默认还有本地规划器

一是保证演示稳定，不依赖网络或额度；二是作为 LLM 方案的基线；三是在高频标准问题上，规则方案成本更低且可预测。产品上可以把高置信度标准问题交给本地规划器，把复杂问题交给 LLM，并对低置信度请求转人工或要求用户补充信息。

## 你在项目中的角色

我承担了从需求定义、PRD、数据与指标设计、Agent工作流、Function Calling Schema、安全策略、界面实现到离线评测的完整过程。技术实现是为了验证产品方案，而核心产品工作是明确用户任务、控制能力边界、定义成功指标和设计可复核的交互流程。

## 项目最大的难点

最大难点不是生成 SQL，而是保证“语法正确”之外的“业务正确”。例如违约率分母、标签成熟度和筛选范围只要有一个口径不一致，结果就会误导业务。我把指标口径从 Prompt 中抽离，做成独立语义层，并让页面同时展示定义、SQL和样本量。这让系统从一次性 Demo 变成了可以验证和维护的产品原型。

## 当前限制

- 默认数据为合成数据，尚未连接真实企业数仓。
- 评测集主要覆盖已登记指标，开放域问题能力有限。
- GPT/Claude 模式需要单独评测成本、延迟和稳定性。
- 缺少真实业务用户的可用性测试与耗时对照实验。
- 生产化仍需接入统一身份、数据权限、监控和审批流程。

## 下一步规划

第一步邀请目标用户完成任务对照实验，验证完成率和耗时；第二步补充多轮澄清，让Agent在问题缺少时间范围或指标口径时主动追问；第三步接入数据权限和元数据服务；第四步建立线上评测集，监控规划准确率、执行失败率、成本和用户反馈。
